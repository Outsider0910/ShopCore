# 设计说明与需求映射

## 1. 需求映射

| 需求 | 实现 |
| --- | --- |
| 官方商店 + 玩家商店 | 主菜单两个入口；官方商品表 / 玩家寄售表分开 |
| 物品严格监听组件 | 数量 1 的 `ItemStack.serializeAsBytes()`；按完整字节匹配、存储、展示克隆 |
| 商店菜单按钮加组件 | `custom_data.shopcore:ui_id` + `custom_model_data` 第 0 个字符串 |
| 资源包按组件值切贴图 | `custom_model_data` 字符串即 UI ID，见 `./components.md` |
| 玩家上架：按钮 → 选物品 → 关闭菜单 → 公屏输入数量/价格 → 确认 | `PLAYER_LIST` 按钮 → 镜像背包选择 GUI → 关闭 → `AsyncChatEvent` 截获 → 可点击确认 |
| 下架：按钮 → 选寄售 → 确认 | “我的上架”/自己的寄售 → 可点击确认 → 删除寄售并进邮箱 |
| 购买：点商品 → 关闭菜单 → 输入数量 → 确认 | 商品点击 → 关闭 → 输入 → 报价 → 可点击确认 |
| 官方商品默认购买数量无限 | `stock = -1`，默认 `per_player_limit = 0` |
| 管理员游戏内上架 | 管理菜单 → 上架官方商品 → 选择背包物品 → 输入单价 |
| 管理员游戏内调规则 | 编辑 GUI：单价/库存/限购/涨价/最高价/重置周期/启停/删除 |
| 限购、随购买次数涨价 | 每位玩家、每个商品、按重置周期统计已购件数；一次多件逐件涨价 |
| 货币兑换 | Wallet 官网资产；配置比例/双向；主菜单入口 → 方向 → 输入源币数量 → 确认 |

## 2. 关键流程

### 2.1 上架

1. 玩家在主菜单/玩家商店点击“上架物品”。
2. 打开 `SELECT_ITEM` GUI，槽位 0-35 镜像玩家主背包。
3. 点击物品 → `player.closeInventory()` → 聊天提示 → `SessionManager` 记录
   `InputType.LISTING` 和物品的完整组件快照。
4. `AsyncChatEvent` 截获下一条聊天，取消广播，主线程解析 `数量 单价`。
5. 校验数量、价格精度、价格上下限、背包中匹配组件物品的总数量。
6. 生成确认会话，公屏发送可点击 `[确认]` / `[取消]`。
7. 点击确认 → 再次校验并扣除背包物品 → 写入 `player_listings`。
8. 写入失败/超出寄售上限 → 物品进邮箱再尝试放回背包。

### 2.2 购买玩家寄售

1. 点击非自己的寄售 → 聊天输入数量。
2. 报价：读取寄售、校验剩余数量、不能买自己的。
3. 确认后：事务内扣减寄售数量并创建 `PENDING` 订单。
4. `ShopEconomy.transfer` 已移除；直接调用 `WalletEconomy.transfer(买家, 卖家, assetCode, 总价, businessNo, reason)`。
5. 成功 → 事务内写买家邮箱 + 订单 `COMPLETED`；失败 → 恢复寄售数量；
   未知 → 订单 `UNKNOWN`，不发货。
6. 买家自动领取邮箱；卖家在线时收到售出提示。

### 2.3 官方商品购买

1. 点击官方商品 → 输入数量。
2. 读取商品、当前周期已购件数，计算逐件价格与总价。
3. 确认后：事务内扣库存、创建 `PENDING` 订单。
4. `WalletEconomy.transfer(买家, null, assetCode, 总价, businessNo, ...)`。
5. 成功 → 邮箱 + 订单完成 + 已购件数累加；失败/未知同上。
6. 限购按“本周期已购件数 + 本次数量”校验；重置周期按配置时区计算。

### 2.4 货币兑换

1. 主菜单“货币兑换” → 列出 `exchange.rates` 与 Wallet 资产合成的方向。
2. 点击方向 → 关闭菜单 → 聊天输入源币数量。
3. 报价：按源币 scale 解析，目标金额 = 源金额 × rate，按目标币 scale 向下取整；
   读取源币余额校验。
4. 确认后：创建 `exchange_orders` PENDING；Wallet `debit` 源币 → `credit` 目标币。
5. 目标币确定失败 → `credit` 退回源币；退款成功订单 FAILED，退款未知订单 UNKNOWN。
6. 成功 → COMPLETED；玩家收到源/目标金额。
7. 只使用 Wallet 官网 `enabled` 资产；商品/寄售各自记录 assetCode。

## 3. 数据表（SQLite）

`plugins/ShopCore/shop.db`：

| 表 | 作用 |
| --- | --- |
| `official_items` | 官方商品模板（完整组件 BLOB）、asset_code、单价、库存、限购、涨价、最高价、重置周期、启停 |
| `player_listings` | 玩家寄售（完整组件 BLOB、asset_code、卖家、单价、剩余数量） |
| `official_purchases` | 每位玩家在每个官方商品上的当前周期已购件数 |
| `orders` | 订单审计：businessNo、asset_code、买卖家、商品模板、数量、单价、总价、状态 |
| `exchange_orders` | 兑换审计：businessNo、玩家、源/目标币与金额、状态 |
| `mailbox` | 待领取物品（完整组件 BLOB + 数量） |
| `meta` | schema 版本等 |

- 所有读写走单线程 DB executor；SQLite WAL；事务覆盖“扣库存/扣寄售 + 建订单”、
  “下架 + 进邮箱”、“订单完成 + 进邮箱 + 累计购买数”等组合操作。
- 订单状态：`PENDING`、`COMPLETED`、`FAILED`、`UNKNOWN`。

## 4. 输入与确认

- 上架：`数量 单价`，分隔符支持空格、逗号、`x`/`×`。
- 购买：正整数，允许 `3个` / `3件`。
- 兑换：源币数量，按源币的 Wallet `scale` 解析。
- 管理员数值：直接输入；库存 `-1` 无限；限购/涨价/最高价 `0` 表示关闭。
- 输入会话默认 60 秒，确认按钮默认 120 秒；可在 `limits` 调整。
- 确认按钮是 Adventure 的 `run_command` 点击事件，执行 `/shop confirm <token>`；
  token 是 UUID，绑定玩家，过期/换人点击都会被拒绝。
- 输入会话被截获时取消聊天广播，避免数量和价格发到公屏。

## 5. 组件与资源包

- UI 物品的 `custom_model_data` 字符串、PDC key、完整 ID 表见 `./components.md`。
- 玩家寄售/官方商品不追加任何商店标记；只在展示克隆上追加 lore。
- 严格匹配口径：完整组件落库为数量 1 的序列化字节；匹配用 Paper
  `ItemStack.isSimilar`（`isSameItemSameComponents`，材质 + 全部组件，忽略数量）。
  数量单独存储。
- 带 `shopcore:ui_id` 的物品禁止上架，避免 UI 物品流通/复制风险。

## 6. 边界与默认值

- 只选择主背包槽位 0-35；盔甲和副手不参与上架选择。
- 玩家寄售单价上架后固定，不支持直接改价。
- 没有交易税、搜索、分类、过期时间、玩家拉黑。
- 官方商品按玩家维度涨价/限购，不是全服维度。
- 玩家商店允许部分购买；剩余为 0 后从列表消失。
- 每个玩家同时最多 28 笔寄售（可配置）；单次数量上限 2304（可配置）。
- 官方商品默认库存无限、限购不限、涨价关闭、重置永不。
- 商城商品价格使用各自选择的 Wallet 官网货币；资产 code/名称/精度来自 Wallet，
  商店不再配置主货币。货币兑换使用 Wallet 的多币种资产（只支持配置里的方向）。
- SQLite 适合单服；如果未来需要跨服共享/高并发，需要把存储层换成 MySQL 并重新设计
  库存锁与事务。

## 7. 需要产品侧确认的点

这些点目前按“建议默认”实现，若要改会涉及 UI/规则文案：

1. 价格是单价还是总价？当前按**单价**，总价 = 单价 × 数量。
2. 官方涨价是按玩家还是全服？当前按**每位玩家当前周期已购件数**，且一次多件逐件涨。
3. 限购单位是“件”还是“笔”？当前按**件**。
4. 下架入口：玩家商店有“下架物品”按钮，主菜单有“我的上架”；两处都打开
   自己的寄售列表。当前按这个实现。
5. 背包满时是掉落还是寄存？当前**寄存到待领取**。
6. 玩家寄售是否允许部分购买？当前**允许**。
7. 官方“默认购买数量无限”是否指库存无限？当前 `stock=-1`，同时默认不限购。
8. 价格精度是否按货币？当前按每种 Wallet 资产的 `scale`，商品/寄售上架时选择货币。
9. 是否需要交易税/手续费？当前没有。
10. 是否需要管理员删除玩家寄售/封禁上架？当前没有，仅有官方商品管理。
11. 兑换比例/双向：`1 源币 = rate 目标币`；双向开启时自动 1/rate 反向，显式反向优先；
    目标金额向下取整。当前按这个实现。

## 8. 测试覆盖

`./gradlew test` 共 42 个用例：

- `AmountsTest`：解析、精度、负数/科学计数法拒绝。
- `PriceCalculatorTest`：无涨价、逐件涨价、已购件数、最高价、精度取整。
- `ResetPeriodTest`：永不/每天/每周/每月窗口与切换。
- `ShopInputParserTest`：上架格式、购买数量、库存/限购输入。
- `ExchangeSettingsTest`：比例/双向/非法费率。
- `ExchangePairFactoryTest`：显式方向、自动反向、显式反向优先、停用资产过滤。
- `ExchangeRateCalculatorTest`：POINT↔CNY、目标精度向下取整、0 金额拒绝。
- `WalletEconomyTest`：同币种买家→卖家付款、跨币种兑换、目标入账失败退款、
  结果未知不退款、余额不足不继续加币、资产精度/格式化、余额缓存刷新与未绑定检测。
- `SqliteShopStorageTest`：官方报价/占位/完成/取消、限购、库存恢复、寄售购买/下架、
  删除寄售后退款回邮箱、寄售上限、不能买自己的、按 asset_code 精度计算、兑换订单生命周期。

服务端验证：

- Paper 26.3 测试服加载插件成功；
- SQLite 驱动由服务端提供，插件无需 shading；
- `/shopadmin reload`、`/shopadmin orders`、Wallet 余额读取与兑换落库正确；
- `/shopadmin debug` 验证 UI 物品的 `custom_data.shopcore:ui_id` 与
  `custom_model_data` 字符串一致；序列化往返后 `isSimilar` 为 true，修改显示名后
  `isSimilar` 为 false（能识别组件变化）；
- Wallet + mock：`POINT → CNY 100` 后 POINT 1000→900、CNY 100.00→101.00
  （Beta_0_3_0 最终验证为 900→800、101.00→102.00）；`exchange_orders` 为 COMPLETED；
  `bidirectional:false` 时反向方向被拒绝且不产生订单；
- GUI 点击流程未接客户端，需人工验收。
